# Data Model: Smart Todo Manager

## Core Entity: Task

| Field | Type | Constraints | Notes |
|---|---|---|---|
| id | string | UUID, generated by server, immutable after creation | Required on persisted records |
| title | string | Non-blank, max 120 chars | Required |
| description | string | Optional | May be empty or omitted |
| priority | enum | LOW, MEDIUM, HIGH | Required |
| status | enum | TODO, IN_PROGRESS, COMPLETED | Required |
| tags | array<string> | Zero or more values | Optional; normalized and deduplicated deterministically |

## Collection Model

The task collection is the persisted list of Task records. It must retain insertion order so equal-priority tasks remain in a stable order after restarts, and every task must remain uniquely identified by its immutable UUID.

## Status Transition Rules

| From | To | Allowed |
|---|---|---|
| TODO | IN_PROGRESS | Yes |
| IN_PROGRESS | COMPLETED | Yes |
| COMPLETED | TODO | Yes |
| same status | same status | Yes (no-op) |
| any other combination | any other combination | No |

Invalid transitions are rejected with HTTP 400 and the stored task remains unchanged.

## Deterministic Behavior Rules

- Tag matching is case-insensitive and uses trimmed lowercase comparison.
- Duplicate tag values are removed while preserving the first-seen order.
- When sorting tasks by priority, `HIGH` is listed before `MEDIUM`, which is listed before `LOW`.
- Tasks with the same priority retain their original insertion order when sorted or reloaded.

## Validation Rules

- Title must be non-blank after trimming.
- Title length must be <= 120 chars.
- Priority must match one of the allowed enum values.
- Status must match one of the allowed enum values.
- Tags must be stored as a collection of strings and must be normalized before persistence.
- Request payloads must not include a task ID during creation.
- Response payloads must not expose mutated stored state when an update request is rejected.

## Persistence Rules

- Storage is file-based JSON only.
- No database is used.
- The JSON file path is configurable and must be provided through configuration rather than being hard-coded in business logic.
- The default runtime JSON file is outside the repository; runtime task data is not application source or a committed test fixture.
- Tests use isolated temporary directories/files for all persistence scenarios and clean them up after execution.
- Persisted records must survive process restarts.
- Safe or atomic writes are required where feasible to avoid partial writes: write to a temporary file then rename it into place.
- Persistence failures must be surfaced and logged; silent data loss is not allowed.
- If the target file contains invalid JSON or cannot be read, the implementation must fail explicitly and preserve the original data.

## Relationships

- One Task Collection contains many Task records.
- Each Task belongs to exactly one collection instance.
- Filter criteria are applied to Task Collection results rather than a separate query model.

## Test Coverage Expectations

The design should explicitly cover:

- normal create/list/get/update/delete flows
- title boundary and trimming rules
- invalid priority and status values
- invalid transitions and rejected updates preserving original state
- tag normalization and deduplication
- missing-resource errors (404)
- persistence read/write failures and restart recovery
